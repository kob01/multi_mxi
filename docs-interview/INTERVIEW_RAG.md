# 面试题与逐字稿答案（RAG 部分）

> 用法：每题给"面试官可能在追问什么"和**逐字稿**（可以直接照着说的口语答案）。
> 所有数字都来自本仓库实现与评测报告，被追问细节能落到具体文件。
> 顺序按面试常见路径排：切块 → 混合检索 → 融合 → 重排 → 阈值与拒答 → 评测 → 存储 → 工程问题。

---

## Q1. 你的知识库切块是怎么做的？为什么不用固定长度切？

**考点**：是否真懂 chunking 的取舍，而不是只会调 splitter。

逐字稿：
我是**两层分块**：父块和子块。父块来自解析出来的**结构单元**——Markdown 按标题层级、PDF 按真实页、Word 按 Heading 样式（中英文样式名都认）、PPT 按幻灯片、Excel 按工作表、字幕按时间轴段落，每个结构单元就是一个父块。父块如果超过 1200 字，再按 512 字、重叠 64 字滑窗切成子块；不超过就一个子块等于父块。检索只命中子块，命中之后按 `parent_id` 组装回父块，喂给 LLM 的是**完整章节**，不是碎片。

为什么不直接用固定长度切：两个原因。第一，固定窗口会**跨章节**——一个窗口里同时装着"报销标准"和"考勤制度"，embedding 被两件事稀释，向量既不够像 A 也不够像 B；第二，切出来的片段本身不是可读的上下文单位，LLM 拿到半句话容易自己补。

我专门做过一组受控 A/B：把同一批底层文本、同一组查询、同一份相关性证据，只改切块规则，一个臂是结构感知、一个臂是 512/64 固定窗口。结果结构感知臂 recall@10 高 13.3%、MRR@10 高 16.0%、nDCG@10 高 17.1%，而且因为边界干净，每查询喂给模型的上下文字符数从 4938 降到 3482，证据密度从 6.7% 升到 10.5%——**又准又省 token**。

我会主动补一句边界：那组实验的语料是拿 MS MARCO 段落按固定种子拼成的伪文档，而 MS MARCO 的正例段落本身就是"小节粒度"，结构感知臂天然跟金标准对齐，所以这个 Δ 是**收益的上界**，准确说是"把一篇结构良好的文档硬用窗口切掉多少质量"，不能当成任意真实企业文档上的通用常数。

## Q2. 为什么要稠密 + 稀疏两路？向量检索不够用吗？

**考点**：对 embedding 失效场景的认知。

逐字稿：
向量检索的强项是语义近似，弱项是**精确字面**。企业知识问答里大量问题是精确字面驱动的：单号 `FIN5000`、`PO3000`、制度条款里的专有名词如"带薪年休假""公积金缴纳比例"、还有型号、代码、人名。这些词一旦被 embedding 摊平到 1024 维空间里，跟一堆语义相近但字面不同的表达挤在一起，BM25 一次 term 命中就能秒杀。

反过来 BM25 也不可靠：同义改写、跨中英、"怎么请假"和"年假申请流程"这种词面不重叠的，纯词频打不出来。所以两路都要，**互为兜底**。

工程上我把 Elasticsearch 明确定位成"可从主库全量重建的派生倒排"：它只存分词后的 `content_tokens`，不存正文，不承担任何事实；ES 挂掉时稀疏通道降级成一个空列表，稠密通道照常服务，对话不会断。这样既拿到 BM25 的收益，又不把它变成硬依赖。

中文分词我没有装 IK 插件：索引侧和查询侧都用 jieba 先切好、用空格拼成一个字符串，ES 侧只需要一个自定义的 `whitespace + lowercase` 分析器就能复现完全一致的词元流。少一个插件，镜像和升级都省心。

## Q3. 两路结果怎么融合？为什么用 RRF 而不是加权分数？

**考点**：是否理解分数不可比这个根本问题。

逐字稿：
用 RRF，公式是 `1/(k + rank)`，我把 k 设成 60，两路各出 top_k=8 的候选，同一块在两路的排名贡献相加，再按融合分取前 8。

不加权分数的原因很直接：**三个尺度不可比**。pgvector 那边我给的是 cosine 距离，越小越相关，范围大概 0 到 2；BM25 是分类型的相关度，无上界，跟语料的词频分布绑定；RRF 融合完又变成 1/61 这种量级的小数。给它们定权重就等于假装它们可比，语料一换、模型一换，权重就失效，而且你没法解释为什么某个块被排到前面。

RRF 只吃排名不吃分数，对分布天然鲁棒，也没有需要调的超参（k=60 是论文里的经验值，作用是让 top1 和 top5 的差距不至于过分悬殊）。我在代码和 README 里都固定了一条口径：**任何检索通道和 RRF 本身都不设阈值**，全链路唯一的一道相关性阈值放在 rerank 后面，因为只有 cross-encoder 输出的 0~1 才有"相关性"的语义，阈值放在那里才立得住。

## Q4. rerank 你是怎么做的？为什么单独起一个 TEI 容器？

**考点**：cross-encoder 认知 + 一次真实的选型踩坑。

逐字稿：
重排用的是 `BAAI/bge-reranker-v2-m3`，真 cross-encoder——把 `(query, 候选文本)` 成对喂进模型的序列分类头直接打分，sigmoid 之后是 0~1 的相关性。推理放在一个独立的 TEI（Text Embeddings Inference）容器里，compose 服务名 `tei-rerank`，暴露 `/rerank` 和 `/health`。

为什么要独立容器，这段有历史：我最初是"伪 rerank"，拿 Ollama 的 `/api/embed` 把 query 和候选都 embed 成向量再做 cosine。两个问题：一它根本不是交叉编码，只是把重排降级成了二次向量比较，分数没有 0~1 的语义，阈值没法定；二那个 reranker 的 GGUF 在 Windows 的 llama.cpp 上**一调用就崩**，每条查询都撞超时，看起来像"重排质量差"，实际是整条通道在降级。所以我否掉了四条路：继续用 Ollama、把模型塞进应用进程（跟业务抢 CPU/GPU）、用 LLM 逐条打分（1+N 次调用，延迟和 token 都不可接受）、以及不重排。最后选 TEI。

实现上有三个点我会强调：

- **一次查询只发一个批量请求**，所有候选一起送，进程级复用一个 `httpx.AsyncClient` 连接池。热路径上每次新建客户端会堆 TIME_WAIT。
- **超时压到秒级**：总超时 3 秒、建连 0.5 秒。因为 rerank 半死不能拖垮整轮对话，抛错就退回 RRF 融合序，并把实际生效的 `score_mode` 写进审计。
- **单批硬截断 32 个候选**，对齐 TEI 默认的 `--max-client-batch-size`，超了会整批 400；溢出的候选不静默丢，保持 RRF 相对序附在尾部。

还有一个隐性不变量很关键：**正文必须在 rerank 之前就位**。我稠密通道只取窄列（不含 `chunk_text`），命中后按主键回表补正文，这一步如果排在 rerank 后面，rerank 拿到的是空串，会被阈值整批裁掉，表现成"查不到相关文档"的静默故障。

## Q5. 只有一个阈值，会不会导致该答的没答上来？拒答怎么设计？

**考点**：RAG 的幻觉治理与"知道自己不知道"。

逐字稿：
我的原则是：**阈值只在"能解释的尺度"上出现一次**，也就是 rerank 之后的 0~1，默认 0.4。实测相关块通常 0.9 以上，噪声通常 0.05 以下，中间地带很窄，所以一个阈值就能干净地把噪声切开。

裁完如果为空，我不把它当成"检索失败"，而是当成一个事实：**知识库里没有相关资料**。这时候编排图上的 judge 有三条边：有块就生成；空集而且重检预算（1 次）还没用，就换一个改写策略重检一次——比如从自然语言问法改成关键词串；重检还是空，或者命中的块被权限全部剔除了，就走**固定话术拒答，根本不进 LLM**，并且返回的参考来源是空列表。

为什么不进 LLM：因为一旦把空上下文交给模型，它就会用参数化记忆编一个看起来很像答案的东西，而且还会配上"根据《XX 制度》"这种引用，这是最危险的一类故障——错得很可信。宁可不答。

我还有一道配套的门禁：检索出口会一次性批量查文档状态，`status != ready` 或者根本没有元数据行的文档视同无权，防止"正在入库的半篇文档"被答出去。另外"越权被全剔"和"库里真没有"我刻意用**同一句拒答文案**，因为告诉用户"有这份文档但你没权限"本身就是信息泄漏。

会不会漏答？会有。但我的取舍是：误拒的代价是用户换个说法再问一次，误答的代价是错误制度被当成公司规定传下去。在企业场景这两个代价不对称。

## Q6. 检索延迟怎么控？P95 大概多少？

逐字稿：
链路上每一跳我都设了独立预算，最慢的那跳决定体验。embedding 是一次 Ollama 调用；稠密通道是 pgvector HNSW 的 TopK；BM25 是一次 ES 查询，两者并行发出；回表是一次主键批量点查；rerank 是一次批量 POST，超时 3 秒。整条混合检索在评测口径下平均 0.6 秒、P95 0.68 秒（top_k=50、top_n=10，比生产配置更重）。生产配置是 top_k=8、top_n=4，更轻。

优化的重点我不放在检索本身，而在**热路径上的重复开销**：一类是缓存，Prompt Cache 把改写和意图兜底这类纯函数调用打掉一次 LLM 往返，Retrieval Cache 命中直接跳过整条检索；另一类是连接复用，rerank、联网抓取都用进程级共享的 `AsyncClient` 池，避免反复建连。

还有一个坑我会主动提：pgvector 加标量过滤（ACL 谓词）会伤召回，因为 HNSW 是在图上按顺序取满足条件的邻居，过滤掉了就得往后走更多。我在会话里 `SET LOCAL hnsw.ef_search = max(100, top_k*8)` 把候选队列放大来补偿，用完显式 `rollback()` 结束这个隐式事务，不污染连接池——否则 `ef_search` 会跟着连接带到下一个请求。

## Q7. 你的评测体系是怎么搭的？指标怎么定义？

**考点**：能不能用数据说话，以及是否知道评测的局限。

逐字稿：
我用 MS MARCO Passage 构造自足样本：从数据集头部按种子随机抽 200 条查询，把它们的正例和负例段落汇成候选池（约 6125 段），落成一个**独立的 PostgreSQL 评测库 + 独立的 ES 索引 + 独立的 Mongo 库**——这点很重要，评测会写数据，绝不能污染业务库。跑的是生产同一套 `HybridRetriever`，只是把作用域换到隔离库。

指标是标准 IR 口径：`Recall@k`、`Precision@k`、`Hit Rate@k`、`MRR@k`、`nDCG@k`、`MAP@k`，k 取 1/3/5/10，报告同时出 JSON 和 Markdown。最近一次 200 查询的结果是 recall@10 0.9625、MRR@10 0.7597、nDCG@10 0.8059、Hit@10 0.9700。

两个方法论上的坚持：

1. **评排序就不要带置信阈值**。评测时我把阈值置 0，保留完整排序列表，否则 `Recall@k` 量的就不再是"排序好不好"，而是"阈值筛得狠不狠"，两件事混在一起没法归因。
2. **A/B 要受控**：做切块对比时，我让两个臂看到**完全相同的底层字节**、相同查询、相同相关性证据，唯一变量是切块规则，这样 Δ 才能归因到切分本身。

我也说局限：MS MARCO 是英文短段落检索，正例本身就是小节粒度，跟我的结构感知切分天然对齐，所以它验证的是"排序与切分机制是否有效"，不等于中文企业长文档上的端到端答案质量；后者要靠真实问答集和 judge 来评，这是我下一步要补的。

## Q8. 为什么用 pgvector 而不是 Milvus / Qdrant？数据量大了怎么办？

逐字稿：
选 pgvector 的核心动机不是"够用"，而是**它能让向量、元数据、ACL、业务表在同一个事务里**。我早期是 MySQL + Milvus 双库，两个痛点很硬：一是入库要跨库写，一边成功一边失败就产生"有元数据没向量"或"有向量没元数据"的孤儿；二是改文档权限时，Milvus 侧不支持原地更新标量，得把整行连向量读回来再 upsert 回去。迁到 PostgreSQL 之后，权限变更就是父子两张表各一条 `UPDATE`，向量列和 HNSW 索引完全不动，一个事务提交。而且我能在 ANN 查询的 `ORDER BY ... LIMIT` **之前**直接下 SQL 谓词做权限前置裁剪，这是独立向量库很难做干净的事。

数据量的答案分两段：

- **扫描成本**：我做了父子双表，`doc_chunks` 只装可检索子块，HNSW 图不再被父块占位（旧单表里父块约占一半且都带着无用的向量）；同时排序扫描只取窄列，`chunk_text` 和 `embedding` 不进扫描集，宽行不拖 IO。
- **正文**：整篇 raw/normalized/structure 和父块全文外置到 MongoDB，PG 只留子块正文。这样同一份正文不会有三个副本（PG、ES、Mongo 曾经各存一份），ES 只存派生分词。

再往上到千万级块，我会明确说：pgvector 需要开始认真评估分区、量化索引（halfvec）或者专用向量库，这是它当前的边界，我不会说它能无限扩。

## Q9. MongoDB 在你的架构里到底承担什么？会不会变成"第四大数据库"负担？

逐字稿：
Mongo 只承担一件事：**正文外置**。三个集合：`doc_bodies` 存整篇 `raw_text`/`normalized_text`/`structure`（超 15MB 溢出到 `doc_body_parts` 分片，避开 16MB 单文档硬限），`parent_texts` 存父块全文，`_id` 直接用 `doc_key`/`parent_id`。

它被刻意设计成**没有检索能力**的门面：只按 `_id`/`parent_id`/`doc_key` 精确批量取，没有全文查询、没有正则、没有聚合，权限语义也一律不在它身上。理由很实在——一旦在 Mongo 上写全文查询或者存权限字段，就会出现"第二套检索"或"第二套权限判断"，那才是真正的运维负担。

降级口径也讲清楚：`mongo_enabled=false` 或者连不上时，读路径返回空，父块上下文退回得分最高子块的文本——答案会变碎但不阻断对话；写路径直接报错，因为入库不能静默丢正文。

至于"为什么不干脆全放 PG"：那些大字段我从来只做主键取回，放 PG 只会持续拖累窄表与 ANN 扫描，收益为零。至于"是不是可以全塞对象存储"——父块全文需要按 `parent_id` 批量精确取，一次组装要拿十几个，KV 批量取是合适的形态，对象存储反而要 N 次请求。

## Q10. 多模态（PDF、图片、视频字幕）是怎么进知识库的？

逐字稿：
解析层统一产出一个 `ParsedBlock(section, page_no, text)` 列表，不同模态只是产出方式不同，后面的归一化、父子切块、向量化、发布全链路共用一套。

- **PDF**：按真实页拆块，记录页码；有文本层直接取，扫描页取内嵌图片走 MinerU OCR。
- **Word**：按 Heading 样式切，中英文样式名（"Heading 1" / "标题 1"）都认，章节路径按标题栈拼。
- **PPT**：按幻灯片；**Excel**：按工作表。这里踩过坑——合并单元格和裸值切块会让表格问答答错列、断行，必须把表头随行带进每个块。
- **字幕/转录**（srt/vtt）：合并成带 `[开始 -> 结束]` 时间轴的 `video_transcript` 块，这样"培训视频里讲报销那段"能按时间戳定位并回答。
- **图片**：整体交给 MinerU 的 `/file_parse` 转 Markdown。图片解析失败我是**明确报错**（上传接口转 502），不静默跳过——用户传了张扫描件，静默返回"没找到相关内容"是最难排查的行为。

还有一点我做的是 offset 一致性：所有 `start_offset/end_offset` 都以 `normalized_text` 为基准，归一化只做保守变换——换行归一、NFKC、剥零宽、去行尾空白、压缩连续空行——绝不删词、换词、重排，保证按 offset 切回来的片段永远是原文的连续子串。并且任何改归一化规则的提交都必须递增 `NORMALIZER_VERSION`，否则全库旧 offset 集体失效。

## Q11. 文档级权限（ACL）具体怎么实现？为什么前置裁剪之后还要再复核一次？

逐字稿：
每条知识块在父子两张表上都冗余四个标量列：`visibility / owner_id / dept_id / allowed_roles`，事实来源是 `documents` 表。可见性四种：`public` 全员、`dept` 指定部门、`role` 指定角色列表、`private` 仅上传者，管理员全量可见，**未知 visibility 一律 default-deny**。

检索时两条通道各有一份**语义逐条对应**的过滤器：pgvector 用 SQL 谓词，作用在 `ORDER BY embedding <=> ? LIMIT k` 之前，无权文档根本不进候选集；ES 用等价的 bool filter（`should` + `minimum_should_match: 1`）。`allowed_roles` 存成逗号包裹的 `,hr,admin,`，PG 侧 LIKE 匹配前必须转义 `%`、`_`、`\`，否则一个含通配符的角色值会把匹配范围放大——这是个安全细节不是格式洁癖。

前置裁剪之后还要复核，是因为**中间步骤会引入新的块**：rerank 之后我把命中的子块组装回父块，父块的正文来自 Mongo、结构来自另一张表，一旦组装逻辑或索引脏数据把不该出现的块带进来，前置裁剪是拦不住的。所以进 Context Builder 前我用同一个 `is_allowed` 逐条再过一遍，剔除项写审计（`acl_final_check_dropped`）。这就是纵深防御：三份实现（SQL 谓词 / ES filter / Python 判定）必须逐条一致，改一处就得同步另两处，并用同一批用例校验。

另外 Retrieval Cache 的 key 里必须带 ACL 签名（`user|dept|role`）——因为命中缓存等于跳过了前置裁剪，如果 key 不含身份，甲用户的私有文档会被复用给乙用户，那就是越权泄漏，不是性能优化了。

## Q12. 重入库和权限变更时，检索侧的一致性怎么保证？

逐字稿：
入库是 **expand-then-contract**，顺序不许违背：

1. 父块全文先写 Mongo（不删旧的）——保证 PG 里可见的行一定取得到正文；
2. 只对 `content_hash` 变了的子块重新 embedding，未变化的从 PG 原样把向量读回来填；
3. PostgreSQL **单事务**发布：先 upsert 父块和子块，再剪除本次不再引用的陈旧行，先删子后删父；
4. 收缩：删掉 PG 不再引用的父块 Mongo 正文。

这么做的直接原因是我早期用"先 `delete_by_doc` 再 upsert"两个独立事务，中间有一个**检索空窗**——旧块已删、新块未发，这时候来的查询就是"库里没有"。同 id 覆盖的常态重入库因此不再有删除窗口。

元数据侧还有发布态门禁：`documents.status` 走 `ingesting → ready`，失败标 `failed`；检索出口批量判 `status != ready` 就视同无权，所以"写了一半的文档"永远答不出去。

权限变更走 `update_acl_by_doc`：同一事务两条 UPDATE 分别打子块表和父块表的四个标量列，向量和 HNSW 索引不动；然后重刷 ES（因为稀疏通道的 filter 字段也在索引里），并 `invalidate_all()` 清 Retrieval Cache。如果子块表匹配 0 行，我会**显式返回 warning** 提示重新入库，而不是静默"改成功了"——那种情况下权限只写进了元数据表，检索侧根本不生效，是最容易骗过人的假成功。

## Q13. 这套 RAG 里你踩过最坑的一件事是什么？

**考点**：真实排障能力，最看重"现象—定位—根因—修复—可复用教训"。

逐字稿（我讲两个，第一个是静默降级类）：
最坑的是 rerank 的**伪实现 + 静默降级叠加**。现象是"重排好像没什么用，答案质量上不去但没有报错"。我是从审计日志里发现每条查询的 `score_mode` 全是 `rrf`，也就是重排从来没真正生效。往下挖：那时重排是借道 Ollama `/api/embed` 拿向量做 cosine，而那个 bge-reranker 的 GGUF 在 Windows llama.cpp 上调用就崩，每条查询都撞超时，异常被我的降级逻辑吞掉成"退回 RRF 序"。所以有**两层问题**：一层是降级逻辑掩盖了故障，一层是这个降级本身根本不是 cross-encoder，分数尺度不对，0.4 的阈值形同虚设。

修复就是把重排拆成独立 TEI 容器，同时定了一条口径：**降级必须可观测**——`score_mode` 随分数标度一并写审计，网关启动时真打一次 `/rerank` 探针（拿一条明显相关和一条明显无关的文本，校验排序对不对），比只查 `/health` 强，能覆盖"服务活着但模型不对（424）/分数全 0"这类故障。

第二个坑是 Excel 表格问答答错列：合并单元格让一片区域只有一个值，按行切块之后每行看到的表头是空的，模型只能猜。修复是切块时把表头随行内嵌进每个块，并对裸值切块做约束。

这两件事我沉淀成一条通用习惯：**先区分"功能坏了"和"配置指错了地址"**。我这整套里 Redis、ES、TEI、Mongo、Neo4j 连不上都是静默退级的，所以我只信两样东西——启动时打印的依赖对接地址快照，和专门的对接自检脚本，不信页面表现。
