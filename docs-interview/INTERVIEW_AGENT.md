# 面试题与逐字稿答案（Agent / 多智能体部分）

> 本文件**不重复讲 RAG 内部技术点**（切块、混合检索、rerank、阈值见 `INTERVIEW_RAG.md`）。
> 这里只讲编排、意图、协议、记忆、权限、流式、安全与工程化。

---

## Q1. 为什么用 LangGraph 而不是自己写 if-else 路由，或者直接用 function calling 循环？

**考点**：编排框架的选型依据，而不是"因为流行"。

逐字稿：
我的拓扑有三个特征是纯 if-else 很难干净表达的：**条件边回环**、**分支汇入同一出口**、**可中断可恢复的状态**。

具体来说，知识库那条链路不是直线：检索 → judge → 要么生成、要么换改写策略重检一次再回到检索、要么明确拒答，这是一个带预算的回环；多智能体分支是用户点选后先扇出（并发委派若干个专业智能体）再在节点内分节合并；最后**所有分支都汇到同一个 `persist_memory`** 写记忆和审计。用 if-else 也能写，但我就得自己维护"当前走到哪、能不能恢复、某一轮的第 3 个节点失败算谁的"这套东西。

LangGraph 给的三样东西正好是我要的：`StateGraph` + 条件边把拓扑显式画出来（可读、可 `draw` 调试）；state 是 TypedDict，每个节点只返回要更新的键，不用改整份上下文；checkpointer 让会话状态天然可持久化。还有一个很实际的好处：**节点即审计单位**，我在每个节点里写一条同 `trace_id` 的审计，链路图跟审计流是一一对应的，排查时能直接定位到节点。

至于"为什么不纯 function calling 循环把所有工具一次性丢给模型"：那样权限、成本、延迟都失控——所有工具都要进 prompt（工具集越大越贵越容易选错），而且写操作和只读操作混在一个工具池里，模型误调就是真实业务动作。我是**分层**的：知识库、MCP 业务域、A2A 委派、进程内能力域各自独立，意图先定域，再在域内让 ReAct 自主选工具，域这一层由白名单锁死。

（顺带一个取舍：并发扇出我没用 LangGraph 的 `Send`，原因见 Q4。）

## Q2. 你的意图识别怎么做的？为什么不每轮直接问一次大模型？

**考点**：成本/延迟/可解释性的三角，以及降级设计。

逐字稿：
三层漏斗加一个终端安全网，按"成本 ÷ 确定性"排序，命中即短路：

1. **规则层**：有序正则表。委派类排在查询类前面，避免"我要报销"被判成查报销单。单号类（`FIN\d+`/`HR\d+`/`PO\d+`/`CT\d+`）和显式格式词（"导出成 excel"）也在这层。命中给 0.9 置信度，**零网络调用**。
2. **语义层**：bge-m3 对代码内置的种子集做最近邻。种子按 `(intent, target)` 分组维护，每个意图取最相似的 Top-3 条求相似度均值作为该意图得分；命中要求**最优得分 ≥ 0.62 且领先次优 ≥ 0.05**。加 margin 是为了防边界样本在两类之间摇摆——只看绝对分会出现"两个意图都 0.61"这种本该下沉却被强行判定的情况。
3. **LLM 层**：DeepSeek 的 JSON 输出，接 Prompt Cache。
4. **fallback**：关键词启发式，保证 LLM 挂了路由也不崩，最差落到 `knowledge_qa`。

为什么不每轮直接问 LLM：三个原因。**延迟**——对话热路径上多一次 LLM 往返就是几百毫秒到几秒；**成本**——意图分类是纯粹的"同一段 prompt → 同一个 JSON"，高频指令没必要付费；**确定性**——"我要报销""帮我开在职证明"这种指令用正则判定是 100% 确定的，交给模型反而可能因为 prompt 抖动漂移。

我还留了可观测：`IntentResult.layer` 记的是 rule / embedding / llm / fallback，落到审计里。误分类的时候我能立刻知道"是哪一层判错了"，而不是只有一个笼统的 intent。第二层任何异常（Ollama 挂、维度不符）只记 warning 后下沉，`intent_embedding_enabled=false` 可以整层关掉。

## Q3. 查询改写（指代消解）为什么放在意图识别之前？失败了怎么办？

逐字稿：
因为**分类和检索都需要消解后的独立问题**。用户第二句问"那帮我查一下它的余额"，如果不消解，分类器看到的是"查一下余额"还是"那它的余额"并不影响它判成 tool_call，但会影响域判定；更严重的是下游——工具调用拿不到查询对象，知识库检索会拿"它"去 embed，检索必然废掉。所以我把改写放在 `resolve_time` 之后、`classify_intent` 与多智能体并发分支之前，让**分类器和全部分派路由共享同一份消解结果**，只做一次。

放在并发委派之前也是有意的：多个智能体拿到的是同一个已消解完指代的问题，下游不需要各自再做一轮消解（否则 N 路委派就要付 N 次消解）。

成本和可靠性：三种情况直接跳过，零额外开销——无历史（首轮）、消息 ≥40 字且不含指代/省略标记（自包含长问题）。标记表只保留真正的上下文依赖信号（人称/指示代词、"上面说的""刚才说"、句尾"呢"），刻意不含"如何/哪个"这类泛疑问词，因为它们大量出现在自包含问题里，会造成无效改写。

失败回退：LLM 异常就用原话，绝不阻断。另外改写结果要**清洗**——剥掉中英文引号书名号、只取第一行、去掉复读的 prompt 前缀（"改写后的独立查询:"），并且拒绝空串、超 200 字、短于 2 字的输出，任一不过就回退原话。因为改写的失败模式不是"报错"，而是"把提示语一起复读回来"，那会污染下游所有 prompt。最后不管有没有改写都写一条 `query_rewritten` 审计，带 `changed` 和 `skipped` 原因。

## Q4. 多个专业智能体并发执行怎么做的？为什么把"自动拆句"下线了？

**考点**：调度口径的可控性，以及承认一条路走不通并把它回收。

逐字稿：
先说我删掉的东西。我原先做过一版**复合问法自动拆分**：`plan_tasks` 节点用一次 LLM 调用把"查我年假还剩几天，明天北京天气怎么样"拆成子问题，逐条走意图漏斗，再按只读/办理分并发与串行执行。跑下来它不好控制：逗号是假阳性高发点，"天安门下次升旗是哪天，时间几点"这种同主体多槽位追问会被拆成两次检索；要压住误拆就得往拆分 prompt 里不断加反例条款，成本随语言现象线性涨，而换来的只是"用户少点一次鼠标"。所以这一整条链（拆分器、任务图校验器、依赖拓扑分层、写操作 deferred 降级）我整体下线了。

留下来的并发执行改成了**显式点选**：调用方（前端多选）在 `ChatRequest.agent_targets` 里给出本轮要问哪几个专业智能体，网关把同一个（已消解指代的）问题并发下发给它们，程序化拼成"一节一个智能体"的 Markdown。四个我认为值得讲的设计：

1. **调度口径零推断**：点选了才走这条路，没点选时行为与改动前完全一致；这一轮也不再跑意图漏斗——分派给谁已经由用户决定，省一次分类开销，也不存在"分类器把多件事判成一个意图"那个老问题了。
2. **委派只有一份实现**：并发分支直接复用单意图路径的 `_delegate_task`，可信身份 metadata、Agent Card 地址覆盖、角色闸门、审计全部同源。自己另写一条分支最大的风险就是漂出第二套委派语义。
3. **并发上限与逐位隔离**：一个委派是一整轮 ReAct（多轮 LLM + 多次工具调用），比一次检索贵得多，所以 Semaphore 默认只放 2；每个委派另有超时与异常隔离，一个智能体挂了、超时、无权、甚至域键写错，都只降级它自己那一节，其余节照常交付。权限不足/非法域/超出可点选上限各自在正文末尾汇总一句——**用户点的每一项都要有交代，不静默吞掉**。
4. **合并不过 LLM**：各节内容已是智能体产出的事实，再过一次模型只会引入改写和编造风险；而且 N 路 token 流交错会糊在一段文本里，所以整篇按点选顺序一次性下发一条 token 事件，前端在 `result` 的 `metadata.agents` 里还能拿到逐个智能体的状态与耗时。

两道超时是故意不同值的：内层 `send_guarded` 用全局 `a2a_timeout`（120s），它回的是一段可读的降级文本，该节仍算"有内容"；外层 `asyncio.wait_for`（150s）只在内层也拦不住时才把那一节判为超时。

本轮的 `IntentResult` 是合成的（`agent_delegate` + 首个智能体 + `layer=explicit`），目的是让落库、审计、前端路由标签的字段形状跟单意图路径一致，不是为了再养一套分类口径。

可点选清单本身也从后端拿：`GET /api/agents` 按 `AGENT_WHITELIST` 过滤，无权智能体根本不摆出来（与"无权工具对 LLM 不可见"同一个口径）；但菜单过滤不当安全控制，真闸门仍在委派时执行。

扇出实现我用的是节点内 `asyncio.gather` 而不是 LangGraph 的 `Send`：分支体本来就得写成 Python helper（要带闸门、超时、隔离），用 Send 还要把这些在图外面再包一层，换不到收益；gather 能在一处控住并发上限、逐位超时、部分失败隔离和分节顺序。

## Q5. MCP 和 A2A 有什么区别？你分别在什么场景用？

**考点**：是否真理解两个协议的定位，而不是当成两个 RPC。

逐字稿：
一句话：**MCP 是"把系统能力标准化成工具"，A2A 是"把有自主决策能力的同行标准化成可委派对象"**。

MCP 我用它封装四个业务域系统：HR 工单、财务报销、数据洞察、采购合同，每个是一个 FastMCP server（streamable-http，容器内 `:8001/:8002/:8005/:8006`，compose 发布到宿主 `18xxx`）。特征是**原子操作**：`create_reimbursement`、`get_leave_balance`、`run_sql`。调用方（我的 Assistant 或专业 Agent）负责决定调哪个、按什么顺序调，MCP server 只管执行和校验业务规则。选它的理由是协议化之后同一套工具不只我能用，任何 MCP 兼容客户端（比如 IDE、别的 Agent）都能直接接，工具发现和 schema 校验由 SDK 负责，新增业务域只是多起一个 server。

A2A 我用它接四个专业智能体（`:9001/:9002/:9005/:9006`）。区别在于**被委派方自己有一个 ReAct 循环**：它会追问、补齐要素、多次调 MCP 工具、自己决定何时算完成。比如 Finance_Agent 收到"我要报销"，会问金额、类别、事由，收集齐了再调 `create_reimbursement`，把单号和审批节点返回。这种"多步办理"用 MCP 表达不了——那等于把整个业务流程硬编码成一个大工具，就失去了对方独立演进的能力。

两个协议上的细节我踩过的：

- **Agent Card 的通告地址不能当路由依据**。卡片里的 `url` 是 Agent 自己写的，在 compose 里通常是容器内服务名（`http://hr-agent:9001`），而 a2a-sdk 的 JSON-RPC transport 就是拿 `card.url` 发 `message/send`。宿主直跑网关 + 容器跑 Agent 时，卡片发现成功、下一步静默失败。我用 `_pin_card_url` 强制以配置端点为准覆盖，两种拓扑都成立，顺带也避免被外部构造的卡片把请求引到非预期主机。
- **可信身份走协议级 `metadata`，不走文本**。`message/send` 的 metadata 里带 `{user_id, role}`，由编排层从可信的 `ChatRequest.role` 写入；用户消息里出现"我是管理员"一律不信，缺失就按 `employee` 最小权限。

另外还有一类能力我**刻意不做成 MCP**：联网检索和文件生成。它们是无状态的基础工具，套一层 MCP 只是多一个容器加一次网络往返，所以我用进程内注册表 `CAPABILITY_TOOLS` 直接注入 ReAct，跳过 MCP 连接池和 MCP 权限矩阵，但共用同一套角色 Mask、Tool Cache 和审计。

## Q6. 多个 Agent / 多个角色之间怎么防止越权？

逐字稿：
我分四层，全部是**默认拒**：

1. **域级白名单**：角色能不能碰这个 MCP server、能不能委派这个 Agent。比如普通员工不允许委派 `analytics_agent`——它能跨 HR/财务/采购查全员经营数据，属敏感能力；但允许委派 `procurement_agent`，因为员工自助提采购单是合理诉求。
2. **角色×工具矩阵**：这是关键的一层——工具未列入某角色的白名单，就**对该角色的 LLM 完全隐藏**，看不见也调不到，而不是调用时报错。原因是如果工具出现在 schema 里，模型可能会在回答里向用户承诺"我可以帮你查预算"，而实际下一调用就被拒，体验和安全都更差。细到 `execute_sql`/`run_sql` 只对管理角色开放，员工的 finance 域只给自助四件套。
3. **文档级 ACL**：知识库检索的权限（另一份材料里讲）。
4. **写操作隔离**：Tool Cache 只缓存只读前缀；A2A 委派整体不缓存；多智能体并发只接受用户显式点选，系统不会自己把一句话扩成多次办理。

还有两个"拒绝也要留痕"的点：MCP 权限拒绝和 A2A 权限拒绝都会写审计（`mcp_permission_denied` / `a2a_permission_denied`）。因为**拒绝是合规上最该留痕的事件**，只把它显示在用户界面上、日志里没有，事后无法回答"谁在什么时候试图越权"。

## Q7. 你的记忆体系分几层？个人记忆是怎么分桶的？

逐字稿：
三层，职责完全不同：

- **Session Memory**：Redis 里的滚动窗口（10 轮）+ 溢出时的 LLM 压缩摘要（超 20 条触发折叠），TTL 1 小时。解决"这段对话说过什么"。
- **Working State**：LangGraph checkpointer，Redis 可用时 `AsyncRedisSaver`，否则退回 `InMemorySaver`。解决"图跑到一半的状态"，让会话能续跑。这里有个硬性前提：Redis 必须是 **redis-stack-server**，`langgraph-checkpoint-redis` 要 RedisJSON + RediSearch 两个模块，裸 redis 会在 setup 时报 `unknown command JSON.SET`。
- **个人级记忆六桶**：画像 / 偏好 / 习惯 / 情节 / 知识 / 图谱。解决"这个用户是谁、有什么长期偏好、发生过什么"，跨会话生效。

六桶的落库分布我特意区分开：画像是一人一条结构化键值，走独立的 `user_profiles` 表、**确定性合并**（按 key 覆盖、单值键受控）；偏好/习惯/情节/知识共用 `long_term_memories` 一张表，用 `kind` 列作桶判别；图谱在 Neo4j，`(:MemoryUser)-[:MENTIONS]->(:MemoryEntity)`。桶语义（kind、注入方式、中文标签、prompt 小节标题）全部声明在 `taxonomy.py` 这一个文件里，召回侧和展示侧都从这里取，避免同一份定义在 prompt 拼接、审计、前端接口三处各写一遍而漂移。

**注入方式按桶不同**，这是我花了最多时间想清楚的一点：

- 画像：全量注入、不检索（每轮带，限 400 字防越滚越大）；
- 偏好/习惯：**标量直读**，按 `last_accessed_at` 取 Top-N，不走 embedding。因为它们跟当轮问题措辞无关——走 embedding 反而会因为问法不同而漏掉"这个用户一贯要 Markdown"这种稳定策略；
- 情节/知识：语义召回，只有跟本轮问题相关才值得进 prompt；情节还额外过时间窗（近 30 天）和衰减降权（超 90 天排序降权，不删数据）。

写路径是一次 LLM 调用产出全部桶的分桶结果，避免多轮抽取的延迟和成本；会话摘要溢出时另存一条情节。有个反直觉的修正：我早期按意图路由把闲聊轮一律跳过提取，结果"我在研发部""以后都用 Markdown 回复"这类自我陈述恰恰会被分类成 chitchat，等于个人记忆永远写不进去；后来改成只挡短消息，无信息量的轮次交给提取 prompt 自己返回空列表。

## Q8. Agent 系统的缓存要注意什么？哪些东西绝对不能缓存？

**考点**：是否理解缓存正确性风险远大于 Web 场景。

逐字稿：
三类缓存都落 Redis，Redis 不可用就退回直连真实调用。但真正的设计工作在"**什么不许缓存**"上，我定了几条硬边界：

1. **知识库生成的输出绝不进 Prompt Cache**。Prompt Cache 的 key 是 `model + temperature + 整段 prompt 的 hash`，它不看权限。而 `kb_generate` 的输出携带了文档级 ACL 的结果和实时检索证据，缓存它等于把"某次权限裁剪后的答案"共享给后续可能无权的查询——这是越权泄漏，不是优化。
2. **Retrieval Cache 的 key 必须含 ACL 签名**（`user|dept|role`）。因为命中缓存等于跳过了两道前置权限裁剪（向量 SQL 谓词和 ES filter），只有同一 principal 能重放自己那份。同时缓存存的是 `chunk_id` 集合，文档重入库会先删后建，旧 id 可能已失效，所以入库路径必须同步 `invalidate_all()`。
3. **写操作工具不缓存**。只认只读前缀白名单 `query_/list_/get_/check_/lookup_/search_`，`create_*`/`submit_*`/`cancel_*`/`generate_*` 天然不命中。理由很直白：缓存"提交成功"的响应复用给下一次调用，用户以为报销单提了两次、后端其实只有一条（或反过来）。代价我也认：像 `precheck_purchase_order` 这种确定性只读工具因为前缀不匹配也不缓存——**无法确认是只读就不缓存**。
4. **TTL 按数据性质分档**：余额、审批进度是实时数据，Tool Cache 只给 30 秒；联网检索结果短期内稳定，web 域单独给 300 秒；Prompt/Retrieval 5 分钟。
5. **A2A 委派整体不接入**：按意图定义它就是"需要专业系统多步办理的复杂业务"（"我要报销""帮我开在职证明"），语义即写/办理；而且我构造的任务文本里带 `[当前时间=...]`，天然每轮不同，接了缓存也几乎不命中。

还有两个"不缓存换来体验"的决定：流式闲聊不读 Prompt Cache，因为命中的重放没有思考过程，缓存收益小于体验损失；多智能体分节合并不再过 LLM，各节已是智能体产出的事实。

## Q9. 流式输出怎么做的？用户刷新页面正在生成的回答怎么办？

逐字稿：
SSE，但关键设计是**把图的执行和 HTTP 连接解耦**。`POST /api/chat/stream` 不直接把模型 token 接到响应上，而是把图丢进后台 asyncio 任务，产生的事件按自增 id 写进进程内的 `StreamHub` 缓冲区；HTTP 连接只是这个缓冲区的一个读者。事件协议里有一条 `run` 事件先下发 `run_id`，前端持久化它。

于是刷新/断网的处理很自然：重连 `GET /api/chat/stream/{run_id}`，带上 `Last-Event-ID`，服务端**先重放已产生的历史事件，再接续实时事件**，直到 run 结束。页面刷新不会丢一次正在生成的回答。缓冲区有保留期（默认 600 秒），过期或服务重启就返回 404，前端降级为拉已落库的会话历史。

实现细节上我做了两个取舍：一是读侧用 50ms 轮询而不是 `Condition`——事件量很小（token 粒度 × 并发 run 数），而 `wait_for(Condition.wait())` 超时取消时有重获锁的边界问题，轮询换掉了这个复杂度；二是明确记录了**代价**：缓冲是进程内的，所以断点续流只在单 worker 部署下有效，多副本要么配 sticky session 要么把缓冲外置。

响应头也带上 `X-Accel-Buffering: no` 和 `Cache-Control: no-cache`，避免 Nginx 之类代理缓冲导致"憋一下全出来"。开发期走 vite dev 代理也能测，因为 http-proxy 是透传不是缓冲。

流式时还顺带透出思考：DeepSeek 通道我用官方 `ChatDeepSeek`（`langchain-openai` 那层不提取 `reasoning_content`），thinking 事件走独立的增量流，最后连同正文一起落进会话记录。

## Q10. Text2SQL 让模型生成 SQL，怎么防注入和拖库？

逐字稿：
这是我最紧张的一条链路，因为 LLM 生成的 SQL 直接对业务库执行。我做了几层，都在**执行之前**：

1. **语句形态**：只允许单条 `SELECT` 或 `WITH ... SELECT`，多语句直接拒。
2. **关键字黑名单（PostgreSQL 方言）**：常规 DML/DDL 之外，专门把 PG 的逃逸面列进去——`SELECT ... INTO`（在 PG 里等价于 `CREATE TABLE AS`）、`COPY`、`pg_sleep`、`pg_read_file`、`lo_import/lo_export`、`current_setting/set_config`、`pg_catalog/pg_class/pg_authid` 等系统目录，以及 `information_schema`、`do/refresh/notify/listen/discard`。黑名单里还留着 MySQL 侧的历史项（`load_file/outfile/benchmark`），因为同一份护栏要防模型"照搬别的方言的招"。
3. **表白名单**：每个 MCP server 传入自己的业务表集合，跨域分析域的白名单横跨 hr/fin/proc 但只读；CTE 别名会被单独识别放行，否则正常写法会被误杀。
4. **行数上限**：结尾没有 `LIMIT` 或超过 50 的，强制改写；结果集不会失控。
5. **语句级超时**：PostgreSQL 没有 MySQL 的 `MAX_EXECUTION_TIME` hint，所以在执行前 `SET LOCAL statement_timeout`（默认 5000ms）注入。
6. **角色维度**：`execute_sql`/`run_sql` 只对管理角色可见，普通员工在 analytics 域一个工具都没有。
7. **权限拒绝留痕**：越权尝试写审计。

有一点我会主动说清：黑名单是**纵深防御里最弱的一层**，它挡的是模型幻觉出来的危险语句和常见逃逸写法，不能当 SQL 注入防护的正解。真正的兜底应该是"用一个只有 `SELECT` 权限的只读角色连库 + 只暴露脱敏视图"。我现在的隔离粒度是表白名单 + 语句校验，下一步要补的是只读角色这一层——这是我知道的现存缺口，不想说成已解决。

另外分析域刻意做成**只读**："分析"与"办理"的分界——统计不改业务数据，写操作一律走业务工具或委派。

## Q11. 有 `fetch_url` 这种让模型给 URL 的能力，SSRF 怎么防？

**考点**：安全题里最容易区分"背过"和"踩过"的一题。

逐字稿：
网关进程的位置很危险——**它身处内网且具备外联能力**：能连 DeepSeek 和 CDN，也持有 PG/Redis/Mongo/Neo4j 的可达路由。让模型随口给一个 URL 就去抓，等于把内网拓扑探测（`http://postgres:5432`）和云元数据窃取（`http://169.254.169.254/`）交给 LLM 的输出。我把护栏做成 `app/security/url_guard.py` 一份唯一实现，任何抓取需求都必须走它，做三件事：

1. **字面名直接拒**（连 DNS 都不查）：`localhost` 系、`host.docker.internal`、以及**全部 compose 服务名**（数据库/缓存/存储/应用/Agent 都列进 deny 表），另外 `*.localhost`/`*.internal`/`*.local` 后缀一并拒。
2. **可选域名白名单**：配置非空时 default-deny，白名单外一律拒，支持子域匹配。这是内网收紧最直接的手段。
3. **解析即校验**：DNS 解析结果逐条 `ipaddress.is_global` 判定，私网/回环/link-local/组播/保留段（含 169.254.169.254）全拒；解析失败也按"不可信"拒。URL 里带 userinfo（`admin:pw@host`）一律拒，既避免凭据外带也防 host 混淆绕过。

最难的是 **TOCTOU / DNS rebinding**：校验和真正建连之间有时间窗，严格做法是"以已校验的 IP 直连"，但 https 要配 SNI/证书，复杂度很高。我采用的是退一步的方案：抓取侧**关闭自动重定向、手动逐跳跟随，每一跳重新过护栏**，响应落地后再对 final URL 复核一次。这把窗口压缩到"单跳内"，攻击者需要控制权威 DNS 才能利用——我把它作为**已记录的残余风险**写进文件头，而不是假装解决了。

还有几个配套约束：`follow_redirects=False` 的共享 httpx 池；重定向上限 3 跳；只接受文本类 `Content-Type`（二进制/压缩包没有抓取价值还烧内存）；响应体和正文字符都有上限（2MB / 8000 字）。**刻意不代理 `fetch_url`**：可选的检索代理只作用于 `search_web`，因为 SSRF 护栏是按容器直连视角解析 DNS 的，走代理会让出口和校验视角不一致，等于自己削弱护栏。

最后一个真实教训：大陆网络下 ddgs 的默认引擎列表全部直连不可达，会逐个超时把整轮拖死；我改成逐引擎独立尝试（任一引擎超时不中断整轮），并把可快达的引擎固化成顺序白名单。检索工具的契约是**永不抛未捕获异常**——一次抓取失败该降级成 `{error}` 载荷交给 ReAct 自己决定，而不是让整轮对话失败。

## Q12. 审计和可观测怎么做的？线上出问题时你怎么定位一次对话？

逐字稿：
两条互补的通道，分工明确：

- **`audit.jsonl`：面向合规留痕**。append-only JSONL，每个节点一条，同一 `trace_id` 串联：`message_received → time_resolved → query_rewritten → intent_classified →（multi_agent_planned / agent_task_completed）→ kb_retrieved / tools_filtered / mcp_dispatch / capability_dispatch / acl_final_check_dropped / mcp_permission_denied / a2a_delegate → personal_context_built / personal_memory_written → turn_completed`。写入前统一过脱敏。定位一次对话就是拿前端返回的 `trace_id` 去 grep 这个文件，整条链路按行顺序就出来了。
- **LangSmith / 自建 Langfuse：面向开发调试与成本分析**。

两条 trace 通道是**并存的独立开关**，这是刻意的：LangSmith 会把对话内容送到外部云，受内网合规约束，容器侧由 compose 字面量**锁死** `LANGSMITH_TRACING=false`，只有开发机在 `.env` 显式打开才生效；Langfuse 是我自建在同一 compose 网络里（`profile=langfuse` 的 6 个容器），对话数据不出本机，所以容器里也可以开。默认两个都关。

Langfuse 接入的两个设计点：一是在图**顶层** `ainvoke` 的 config 上挂 LangChain `CallbackHandler`，回调会沿 LangGraph 传播到所有子 run（意图识别、检索、ReAct 工具、MCP、A2A），一轮对话归并成**一条 trace**，而不是散落 N 条；二是 trace id 由审计的 `trace_id` 经 `Langfuse.create_trace_id(seed=...)` **确定性派生**，同时把原始 `trace_id` 也写进 trace metadata，所以从审计日志能直接跳到 Langfuse 对应 trace，反过来也行——两条系统能互相定位才有意义。降级口径与全仓一致：未启用、未配密钥、没装包，`langfuse_callback()` 返回空 dict，config 里 `**` 展开即无操作，上报失败只告警。

还有个踩过两次以上的坑值得讲：Langfuse v4 默认 `events_only` 写入模式，v3 时代的 `/api/public/traces` 列表/详情接口实测 404，程序化读回必须走 `observations` 接口按 `trace_id` 取全链路节点。这种版本差异不看实际行为、只看文档就会白排查半天。

另外网关启动时会打印一行**依赖对接地址快照**（只打地址不打密钥，密钥字段已 `repr=False`）。因为降级是静默的，只看结果无法区分"功能坏了"和"配置指到了另一轨的地址"，这一行就是对照现场配置的快照。

## Q13. 部署形态怎么定的？为什么不上 K8s？

逐字稿：
现在的形态是 **Docker Compose 单机 16 个服务**：网关 assistant、4 个 MCP、4 个 A2A Agent、postgres、elasticsearch、redis、neo4j、mongo、tei-rerank、mineru（另有 `profile=langfuse` 的 6 个可选容器）。宿主机只跑两样：vite dev 和 Ollama——embedding 留在宿主是因为本地模型加载慢且吃显存，容器频繁重建不值得。

为什么 compose 不上 K8s：交付目标是**内网单机可复现**——一条 `up -d --build` 就能起完整链路，评测、演示、客户环境验证都靠这一条命令。K8s 带来的收益（弹性调度、滚动发布）在我这个规模上还不抵它的运维与交付复杂度。但我并没有把自己锁死：服务边界已经按"一个服务一个职责"划好，迁移时逐个映射成 Deployment + Service，应用类服务可以 `kompose convert` 转完人工校对；`OLLAMA_BASE_URL` 指向集群内推理服务地址即可，应用代码不用改。真正需要重新设计的是有状态组件（PG/ES/Mongo/Neo4j）——那部分该用集群托管存储而不是沿用卷。

配置管理上有两条我认为必须坚持的纪律：

1. **配置分双轨且不许混**：宿主侧 `.env` 是宿主视角（全部指向 docker 已发布端口，供宿主侧脚本和评测用）；容器侧靠 compose 的 `env_file` + `environment` 注入服务名地址。两侧地址不同是**故意的**，任何一侧混进另一侧的地址都会让对应层静默降级。这里踩过一次很典型的坑：pydantic-settings 是后读的 `.env` 覆盖前面的，如果把 `docker/.env` 加进 `env_file`，容器服务名会被灌进宿主进程。
2. **红线键在 compose 里字面量锁死**，不允许 `${VAR:-default}` 插值——因为 shell 里残留的同名 export 会赢过代码默认值，表现同样是静默降级。配套一个 `env-check` 自检扫 compose 源，红线键那行若含 `${` 直接 FAIL。

密钥一律只住 `docker/secrets/*.txt`，compose secrets 挂到 `/run/secrets/*`，`Settings` 的 `field_validator` 先读挂载路径、再回退宿主相对路径，dotenv 里同名字段留空；打包脚本另有两道闸门（源侧明文密钥审计 + 产物扫描 `sk-`/私钥体/DSN 口令/云 AK），任一不过即中止且不产出包。

还有一个纯环境的坑：Windows 的 `winnat`/Hyper-V 每次开机把整段端口写进 TCP 排除范围，段内端口即使无人监听也无法 bind，Docker 报 `ports are not available` 然后容器卡在 `Exited(255)` 且**没有任何应用日志**。排除段每次开机都可能变。所以宿主发布端口抬到 `18xxx`/`17xxx`，并且排查第一步是 `netsh int ipv4 show excludedportrange protocol=tcp`。

## Q14. 容器是唯一的验证环境，这句话具体约束了你什么？

逐字稿：
这是一条我给自己立的工程纪律，起因是同一个 bug 在宿主和容器里结论相反。

三条硬规定：

1. **禁止在宿主机直跑网关（`uvicorn app.main:app`）做代码验证**。因为宿主轨和容器轨的配置视角不同，宿主上跑通不代表容器里正确，反之亦然；用宿主结论代表容器行为会得出错误判断。
2. **改过任何 `app/` 代码必须重建镜像再看结果**（`dev.ps1 -Build`）。容器里跑的是镜像快照，没有热重载兼容层——"改了没反应"第一嫌疑就是忘了 `-Build`。
3. **验证先跑对接自检，别看页面表现**：`dev_services check` 会逐个探依赖并打印真实地址；降级是静默的，页面能聊不代表 Redis/ES/TEI/Mongo 都在。

唯一两个例外是前端 vite dev（必须宿主跑，开发体验优先）和 Ollama（不在 compose 内）。

这条纪律带来的收益不是"规范好看"，而是把一类最难复现的故障——**配置指向了另一轨的地址导致静默降级**——变成可以在启动日志里一眼看到的问题。

## Q15. 这个 Agent 系统现在还有哪些不足？如果重做会改什么？

**考点**：技术判断力与自我认知。答得越具体越好，避免"没有不足"。

逐字稿：
我列五条，按影响排序：

1. **SSE 事件缓冲在进程内，只支持单 worker**。多副本要 sticky session 或把缓冲外置（Redis Stream 是自然选择，改造成本可控）。目前我把它作为明确记录的代价，而不是缺陷。
2. **Text2SQL 的隔离粒度不够硬**。现在是"黑名单 + 表白名单 + LIMIT + statement_timeout"，缺**只读数据库角色 + 脱敏视图**这一层。黑名单只是纵深防御里最弱的一环，不能当正解。
3. **长期记忆默认关闭**（`long_term_memory_enabled=False`），只在 docker/.env 里显式打开。这意味着六桶记忆的召回质量我还没有在真实多轮数据上充分验证，只有开关和降级路径是稳的。
4. **鉴权是"可信上游假设"**。`ChatRequest` 直接带 `user_id/role/department`，我内部按它做权限，但生产必须换成统一身份系统签发的凭证（JWT/OIDC）+ 服务端解析，绝不能信任客户端传的 role。生成物下载也是"32 位 hex 能力令牌"这个最小访问面，身份绑定强校验还在待办里。
5. **评测口径的局限**。MS MARCO 是英文短段落，正例天然小节粒度，验证的是排序与切分机制，不等于中文企业长文档的端到端答案质量。要补的是真实问答集 + LLM judge + 引用正确率的人工抽检。

如果重做，架构上我不会改的三件事：一入口分层调度、"唯一阈值只作用于 rerank"、"能降级就降级 + 降级必须可观测"。会改的两件事：第一，**从一开始就用只读 DB 角色和视图层**接 Text2SQL，而不是靠应用侧黑名单；第二，**身份与权限从第一天就走 metadata/凭证**，不要留"客户端传 role"这种临时口子——后面所有权限逻辑都会默认信它，越晚换越贵。
