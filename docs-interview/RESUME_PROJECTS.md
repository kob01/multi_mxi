## A1. 简历精简版 · 项目一（RAG）

**企业级多模态 RAG 知识底座（自研检索 + 生成链路）** · 独立设计与实现
技术栈：Python 3.11 / FastAPI / LangChain / PostgreSQL+pgvector / Elasticsearch / MongoDB / Redis / Neo4j / Ollama(bge-m3) / TEI(bge-reranker-v2-m3) / MinerU / Docker Compose

- 设计**混合检索链路**：pgvector 稠密 ANN（cosine + HNSW）与 Elasticsearch BM25 稀疏通道并行召回，RRF（k=60）融合排名后由 cross-encoder 重排；稠密通道只扫窄列、命中再按主键回表补正文，避免宽行进入向量排序扫描，同时用 `SET LOCAL hnsw.ef_search` 补偿标量过滤带来的召回损失。
- 提出并落地**"全链路唯一相关性阈值"**策略：各通道分数尺度不可比（余弦距离 / BM25 / RRF），因此只在 rerank 之后设一道 0~1 置信阈值（默认 0.4）裁噪声；裁空即"未检索到相关文档"这一事实，交给上层 judge 换改写重检一次，仍空则用固定话术拒答且不进 LLM，从根上杜绝"噪声变小说"。
- 实现**结构感知父子分块 + 正文三层存储**：多模态解析（md/pdf/docx/pptx/xlsx/字幕/图片 OCR）产出 section 级父块，超限父块滑窗切子块；父块全文与整篇 raw/normalized/structure 外置 MongoDB，PostgreSQL 只留可索引窄行与子块正文，ES 为可全量重建的派生倒排；入库走 expand-then-contract 单事务发布，消除重入库的检索空窗。
- 建设**文档级 ACL 与发布态门禁**：`visibility/owner_id/dept_id/allowed_roles` 四个标量列冗余在父子两表，向量 SQL 谓词、ES bool filter、Python 逐条复核三份实现语义逐条对应；权限热更新降为同事务两条 UPDATE（不动向量与 HNSW 索引），进入 Context 前二次复核并区分"越权"与"库里没有"以避免存在性泄漏。
- 搭建**可复现的检索评测体系**：基于 MS MARCO 段落构造受控样本，在**独立 PostgreSQL 库 + 独立 ES 索引 + 独立 Mongo 库**上跑 Recall/Precision/Hit/MRR/nDCG/MAP@k 与切块策略 A/B；结构感知切分相对固定窗口切分 recall@10 +13.3%、MRR@10 +16.0%、nDCG@10 +17.1%，同时上下文长度下降约 29%、证据密度提升 57%。
- 工程化：中文 BM25 用 jieba 预分词 + 空格拼接（免装 IK 插件）、rerank 迁到独立 TEI 容器（真 cross-encoder，秒级超时 + 失败降级 RRF 序）、Retrieval Cache 以 ACL 签名为 key 并随入库失效、Docker Compose 一键起全栈并做对接自检。

## A2. 简历精简版 · 项目二（Agent）

**企业级多智能体助手（Assistant 一入口分层调度）** · 独立设计与实现
技术栈：Python 3.11 / FastAPI / LangGraph / LangChain / MCP(FastMCP) / A2A(Agent2Agent) / Redis Stack / Neo4j / PostgreSQL / Vue3 / Docker Compose / LangSmith + 自建 Langfuse

- 用 LangGraph 编排**单一入口的分层调度图**：`build_context → resolve_time → rewrite_query → classify_intent → 分派（知识库 / MCP 工具 / A2A 委派 / 直答） → persist_memory`，调用方显式点选智能体时改走 `multi_agent_execute` 并发分支；每个节点写审计并以同一 `trace_id` 串联；指代消解与平台时钟**前置于意图识别**，让分类器与全部路由共享同一份消解结果。
- 实现**三层意图识别漏斗**：规则快筛（高频固定指令，零网络调用）→ bge-m3 种子集语义分类（Top-K 相似度均值 0.62 命中 + 领先次优 margin 0.05 防摇摆）→ LLM 兜底 + 终端关键词安全网；逐层可单独关停、逐层降级，命中层级 `layer` 落审计，兼顾成本、延迟与可解释性。
- 设计**多智能体并发委派**：调用方（前端多选）在 `agent_targets` 里显式点选本轮要问的专业智能体，同一个已消解的问题用 `asyncio.gather` 并发下发，分节合并不再过 LLM（避免改写与编造）；Semaphore 并发上限 + 逐位超时 + 异常隔离，一个智能体失败只降级它自己那一节；权限不足/非法域/超出可点选上限均逐节明写。曾实现过一版 LLM 自动拆句（拆分器 + 任务图校验器 + 依赖拓扑分层），因误拆难控、需不断加提示词反例而**主动下线**，改为可完全预期的显式点选。
- 落地 **MCP 与 A2A 双协议协作**：4 个 FastMCP 业务域服务（HR 工单 / 财务报销 / 数据洞察 / 采购合同，streamable-http）+ 4 个 A2A 专业智能体（Agent Card 发现 + JSON-RPC `message/send`）；身份经协议级 `metadata` 下发而非文本、Agent Card 通告地址强制被配置端点覆盖（防被外部卡片引流）；Text2SQL 走只读护栏（单条 SELECT、关键字黑名单、表白名单、强制 LIMIT 与 `statement_timeout`）。
- 构建**三层记忆 + 三类缓存**：Session Memory（Redis 滚动窗口 + 溢出 LLM 摘要）、Working State（LangGraph AsyncRedisSaver checkpoint，退回 InMemorySaver）、个人级六桶记忆（画像走 `user_profiles` 确定性合并，偏好/习惯/情节/知识共用 `long_term_memories` 的 `kind` 列，图谱落 Neo4j；读路径并行召回、写路径一次 LLM 提取分桶落盘）；Prompt/Retrieval/Tool 三类缓存统一落 Redis，且明确"只缓存无权限判定的纯函数调用、写操作与 A2A 整体不缓存"。
- 治理与工程化：角色×工具双层白名单（默认拒，隐藏工具对 LLM 不可见）、文档 ACL、身份证/银行卡/手机号/金额脱敏（保留 URL 段防链接被打码撕坏）、SSRF 三重护栏 + 逐跳重定向复核、Append-only JSONL 审计 + LangSmith/自建 Langfuse 双通道可观测、SSE 流式与断点续流（事件缓冲 + `Last-Event-ID` 重放）、compose secrets 管密钥、容器为唯一验证环境的配置双轨与 env-check 自检。

## B. 技术选型理由（每个选择解决了什么问题）

### B1. RAG 项目

| 选型                                                     | 替代方案                                                                              | 为什么选它 / 解决了什么问题                                                                                                                                                                                                                                                                                                                 |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **bge-m3（Ollama 本地推理）**                            | OpenAI embedding API、BGE-M3 自建服务                                                 | 中英混排企业文档、8k 长上下文、原生多语；1024 维稠密向量本地跑避免数据出内网、无按 token 计费；Ollama 只承担 embedding 这一件事，接口 `/api/embed` 支持批量                                                                                                                                                                                 |
| **pgvector（PostgreSQL）作向量库**                       | Milvus / Qdrant / 独立向量服务                                                        | 向量与文档元数据、ACL 标量列、业务表**同库同事务**：原本是 MySQL+Milvus 双库，需跨库同步且 ACL 变更要"读回整行含向量再 upsert"；换成 PG 后 ACL 变更就是一条 `UPDATE`，且能在 ANN 的 `ORDER BY ... LIMIT` 之前直接下 SQL 谓词做前置权限裁剪                                                                                                  |
| **窄列 ANN + 主键回表**（关键实现约束）                  | 一次查询把正文一起捞出来                                                              | `chunk_text` 是宽行，进入排序扫描会放大 IO/TOAST 读；只取 `NARROW_COLUMNS`（不含正文与向量），命中后再按 `chunk_id` 主键批量点查补正文。约束是**回表必须在 rerank 之前**，否则 cross-encoder 拿到空串会被阈值整批裁空，表现为"静默找不到文档"                                                                                               |
| **Elasticsearch 做 BM25 稀疏通道**                       | PG `tsvector`、只上向量检索                                                           | 向量对专名/编号/精确词命中差（"FIN5000""年休假"这类必须字面命中）；BM25 依赖语料级 df/avgdl 与 Lucene 段文件管理，独立常驻服务才合适。定位为**可从 PG 全量重建的派生索引**，不承载事实，因此 ES 挂了只让稀疏通道降级为空、稠密通道仍服务                                                                                                    |
| **jieba 预分词 + whitespace 分析器**                     | 装 IK / 中文分词插件                                                                  | 索引侧与查询侧都用 jieba 切好再以空格拼接，ES 只需自定义 `whitespace + lowercase` 就能复现同一词元流；少一个镜像插件，版本升级与运维都不受影响                                                                                                                                                                                              |
| **RRF(k=60) 融合排名**                                   | 加权分数融合                                                                          | 余弦距离、BM25 分、rerank 分三个尺度**不可比**，加权必然失准；RRF 只融合排名，对分数分布天然鲁棒、无需调权重超参                                                                                                                                                                                                                            |
| **TEI 容器跑 bge-reranker-v2-m3（真 cross-encoder）**    | ① Ollama `/api/embed` 取向量做 cosine 的"伪 rerank"；② LLM 打分排序；③ 内置进应用进程 | ①不是交叉编码，分数无 0~1 语义，且该 GGUF 在 Windows llama.cpp 上调用即崩；②每条候选一次生成，延迟与 token 成本不可接受；③把推理塞进网关会让 CPU/GPU 与业务进程互相抢资源。TEI 独立容器：一个批量请求打完所有候选、`raw_scores=false` 直接给 sigmoid 相关性、进程级复用 `AsyncClient` 连接池、总超时压到 3s（建连 0.5s），失败降级为 RRF 序 |
| **单批上限 32 候选（对齐 TEI max-client-batch-size）**   | 全量送打分                                                                            | 超过会整批 400；生产 `top_k=8` 远未触顶，评测拉高 top_k 时溢出候选保持 RRF 相对序附在尾部、不静默丢                                                                                                                                                                                                                                         |
| **父子分块（检索子块 / 组装父块）**                      | 只用固定长度小块                                                                      | 小块利于语义精准命中但截断上下文，大块利于完整性但 embedding 被稀释。父块=章节、子块=滑窗 512/overlap 64；命中的子块按 `parent_id` 组装回完整章节喂给 LLM                                                                                                                                                                                   |
| **结构感知切分（按标题/页/工作表）**                     | 固定窗口硬切                                                                          | A/B 实测：同一批底层字节只改切块规则，recall@10 +13.3%、MRR@10 +16.0%、nDCG@10 +17.1%，MAP@10 +20.6%；且上下文更短（3482 vs 4938 字符/查询）、证据密度更高（0.105 vs 0.067），省 token 又答得准                                                                                                                                             |
| **MongoDB 承载正文外置**                                 | 正文全塞 PG 单表 / 塞 ES                                                              | PG 的价值在可索引窄行与事务，整篇 `raw/normalized/structure` 与父块全文是"只按 `_id` 取、从不检索"的大字段，放 PG 会持续拖累 ANN 扫描；Mongo 按 `parent_id` 精确批量取，超 15MB 溢出分片，天然不承载权限语义（避免第二套权限判断）                                                                                                          |
| **offset 基准 = normalized_text + `NORMALIZER_VERSION`** | 直接对 raw 记 offset                                                                  | 归一化（换行/NFKC/剥零宽/压空行）只做保守变换不删词不重排，保证切片仍是原文连续子串；版本号与规则同升降，否则改一次归一化会让全库旧 offset 集体失效                                                                                                                                                                                         |
| **expand-then-contract 单事务发布**                      | 先 `delete_by_doc` 再 upsert                                                          | 两个独立事务之间存在"旧块已删、新块未发"的检索空窗；改成正文先落 Mongo → PG 单事务 upsert 父子 + 陈旧剪除（先子后父）→ 收缩不再引用的 Mongo 正文，PG 可见的行一定取得到文本                                                                                                                                                                 |
| **增量 embed（按 `content_hash`）**                      | 每次全量重 embed                                                                      | embedding 是最慢一环（Ollama 批量 64 条/请求，大文档上千块）；哈希未变的子块直接从 PG 原样回填向量，重入库只打变化的块                                                                                                                                                                                                                      |
| **ACL 走标量列 + 三份等价实现**                          | 权限写进 JSONB / 只在一处判                                                           | 权限字段进 JSONB 无法建索引也易被绕过；SQL 谓词 / ES bool filter / Python `is_allowed` 逐条对应，任何一处改动必须同步另两处，否则就是越权事故                                                                                                                                                                                               |
| **MS MARCO + 独立评测库**                                | 在生产库上跑评测 / 只看主观样例                                                       | 独立 PG 库 + 独立 ES 索引 + 独立 Mongo 库做隔离，指标（Recall/Precision/Hit/MRR/nDCG/MAP@k）可复现，切块与阈值改动有 A/B 依据而不是凭感觉；评测时把阈值置 0 以免 @k 指标被置信裁剪污染                                                                                                                                                      |
| **多模态解析 + MinerU OCR**                              | 只吃纯文本                                                                            | pdf 按真实页、docx 按 Heading 样式（中英文）、pptx 按幻灯片、xlsx 按工作表、srt/vtt 带 `[开始->结束]` 时间轴；无文本层的扫描件与图片走 MinerU `/file_parse`，服务不可用则明确报错（502）而不是静默丢内容                                                                                                                                    |

### B2. Agent 项目

| 选型                                               | 替代方案                                            | 为什么选它 / 解决了什么问题                                                                                                                                                                                                                                                                                       |
| -------------------------------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LangGraph 编排（StateGraph + 条件边）**          | 线性 pipeline / 纯 function calling 循环 / 自研路由 | 需要**可分支、可回环、可 checkpoint**的拓扑：retrieve-judge-requery 是条件边回环，多智能体并发是一个独立分支；节点即审计单位，状态是 TypedDict，天然支撑"每个节点写一条 trace_id 相同的审计"                                                                                                                            |
| **Redis Stack 作 checkpointer（AsyncRedisSaver）** | PostgresSaver / 不做持久化                          | 会话中断续跑与多轮状态需要秒级读写；选它的前提是必须带 RedisJSON + RediSearch 两个模块（裸 redis 会在 setup 时报 `unknown command JSON.SET`），因此不可用时退回 `InMemorySaver`，代价是不持久化                                                                                                                   |
| **三层意图漏斗（规则→embedding→LLM→关键词）**      | 每轮直接问 LLM 分类                                 | 高频固定指令（"我要报销""FIN5000 到哪了"）走规则 0ms 且确定性最高；标准问法一次 embedding 命中；只有长难句下沉 LLM。结果是成本/延迟显著下降，且每条判定带 `layer`，误分类能在审计里定位到层                                                                                                                       |
| **bge-m3 种子集做语义层（Top-K 均值 + margin）**   | 训练一个分类器 / 只用 prompt 分类                   | 意图体系小且随版本演进，代码内置种子表即可维护、无需训练数据与额外服务；要求"最优过阈值 **且** 明显领先次优"才命中，防止边界样本在两类间摇摆；Ollama 挂了就整层跳过                                                                                                                                               |
| **多智能体交给用户点选，不做自动拆句**         | LLM 自动拆复合问法 + 代码校验器                   | 拆句准确率靠提示词里不断堆反例（同主体多槽位追问被拆成两次检索），成本随语言现象线性涨而收益只是"少点一次鼠标"；显式点选零推断、完全可预期，无权/非法域/超上限都逐节明写。已实现过的拆分链整体下线                                                                                              |
| **节点内 `asyncio.gather` 扇出**                   | LangGraph `Send` API                                | 并发分支体本来就得写成 Python helper（要带闸门、超时、隔离），用 Send 还要把这些在图外再包一层，换不到收益；gather 能在一处控住并发上限、逐位超时与部分失败隔离，还能保证分节顺序                                                                                                                                               |
| **MCP（FastMCP + streamable-http）**               | 各家私有 function schema / REST 直连                | 业务系统能力协议化后，同一套工具既能被本项目 ReAct 用，也能被任何 MCP 兼容客户端复用；工具发现、schema 校验、连接池由 SDK 负责，新增业务域只是加一个 server                                                                                                                                                       |
| **A2A（Agent Card + JSON-RPC `message/send`）**    | 把专业智能体做成一个大函数                          | 专业智能体是**独立进程、独立权限边界、独立演进**的服务：卡片让能力可发现，metadata 让可信身份走协议而非文本；卡片通告地址不作路由依据（统一按配置端点覆盖），否则宿主直连时会被容器内服务名带到静默失败的下一步                                                                                                   |
| **进程内能力域（web/docgen）而非再开容器**         | 每个能力都做成 MCP server                           | 联网检索与文件生成是无状态的基础工具，套一层 MCP 只是多一个容器与一次网络往返；用 `CAPABILITY_TOOLS` 注册表直接注入 ReAct，跳过连接池与 MCP 权限矩阵，但共用同一套角色 Mask / Tool Cache / 审计                                                                                                                   |
| **docgen 域并入只读检索工具**                      | 只给 `generate_*`                                   | "调研 X 并导出 PDF"被判成 docgen 后，如果本域只能生成，ReAct 只能凭模型记忆编内容再落盘（答非所问且看似秒回）；补入 `search_web/fetch_url` 后同一轮可先检索再据实成文                                                                                                                                             |
| **三层记忆（Session / Working State / 个人六桶）** | 只做窗口拼接                                        | 窗口解决"这轮说过的话"；checkpoint 解决"跑到一半的状态"；六桶解决"这个用户是谁、有什么偏好、发生过什么"（画像/偏好/习惯/情节/知识/图谱）。读路径并行召回、各桶单独降级，写路径一次 LLM 提取分桶落盘，避免多轮调用                                                                                                 |
| **画像确定性合并（不交给 LLM 重写）**              | 每轮让 LLM 重总结画像                               | 画像是结构化键值（一人一条），LLM 重写会随机丢字段且无法审计；确定性合并按 key 覆盖、单值键受控，渲染成 prompt 片段时限 `profile_max_chars` 防越滚越大                                                                                                                                                            |
| **情节带 `occurred_at` 时间锚 + 时间窗/衰减**      | 一律按相似度召回                                    | "上周报的销"这类事必须锚定发生时间；召回只取近 30 天、超 90 天降权（仅影响排序不删数据），陈年旧事不再挤占 prompt                                                                                                                                                                                                 |
| **三类缓存 + 明确的"不缓存"边界**                  | 全量缓存 LLM/工具结果                               | Prompt Cache 只给"同 prompt→同结果"的纯函数调用（改写/意图兜底/闲聊），**严禁知识库生成**（输出携带 ACL 与实时检索结果，缓存等于越权共享）；Retrieval Cache 的 key 必须含 ACL 签名，命中会跳过前置裁剪；Tool Cache 只认只读前缀，`create_*/submit_*/generate_*` 天然不命中，A2A 委派整体不接入（语义即办理） |
| **SSE + 事件缓冲断点续流**                         | WebSocket / 直接返回最终答案                        | 刷新/断网不该让一次生成报废：图在后台任务跑，事件按自增 id 落进程内缓冲，HTTP 连接只是读者，凭 `Last-Event-ID` 先重放后续读；缓冲过期则前端降级为拉已落库的历史（单 worker 部署有效，这是明确记录的代价）                                                                                                         |
| **角色×工具双层白名单 + 默认拒**                   | 传 JWT / 让 LLM 自觉                                | 工具未列入某角色白名单就对该角色**完全隐藏**（看不见也调不到），比调用时报错更安全——LLM 不会因为看见工具而在回答里承诺能力；`execute_sql/run_sql` 可跨全员取数属敏感，只对管理角色开放                                                                                                                            |
| **审计 JSONL + LangSmith/自建 Langfuse 双通道**    | 只留一种                                            | `audit.jsonl` 面向合规留痕（append-only、脱敏后入库）；LangSmith 面向开发调试但会把对话送到外部云，容器侧锁 false；Langfuse 自建在同一网络内、数据不出本机，容器也可开。trace id 由审计 `trace_id` 确定性派生，两个系统可双向跳转                                                                                 |
| **容器为唯一验证环境 + 配置双轨**                  | 宿主机直跑验证                                      | 宿主轨与容器轨的地址视角不同，宿主结论对容器部署不成立，且 Redis/ES/TEI/Mongo 连不上时是**静默降级**，只看页面表现无法区分"坏了"与"指错了地址"；因此网关必须跑在 compose 内，compose 红线键字面量锁死（防 docker/.env 覆盖不动），启动打印对接地址快照 + `env-check` 自检                                         |
| **Docker Compose 单机编排（16 个服务）**           | K8s                                                 | 交付目标是内网单机可复现：一条 `up -d --build` 起网关/4 MCP/4 Agent/6 个存储与推理服务；密钥走 compose secrets 挂 `/run/secrets/*`（不进镜像/环境变量/git），端口抬到 18xxx/17xxx 规避 Windows `winnat` 的 TCP 排除段；需要迁 K8s 时服务边界已按 Deployment+Service 划好                                          |
| **Vue3 + Vite + Element Plus，网关只托管构建产物** | 服务端模板渲染                                      | 开发期走 vite dev（代理到容器发布端口，SSE 是 http-proxy 非缓冲透传，断点续流可测），生产期有 `web/dist` 才托管 SPA、否则明确提示该起 dev server，避免"GET / 直接 500"掩盖真实原因                                                                                                                                |

**引用这些数字时建议附带的两句边界（面试官很可能顺着问）：**

1. A/B 的语料是把 MS MARCO 段落按固定种子分组成伪文档，正例段落本身就是"检索粒度的小节"，结构感知臂天然与金标准对齐 —— 因此这组 Δ 是**结构感知切分收益的上界**，精确度量的是"把结构良好的文档用固定窗口硬切的代价"，不能外推成任意真实企业文档上的通用常数。
2. 那两次评测的本机 reranker 不可用（历史 Ollama GGUF 崩溃问题），实际跑的是 dense + BM25 + RRF；两个臂口径一致所以 Δ 可信，但**绝对值会比加了 rerank 的线上端到端略低**。
